# Skill: 세션 분할 및 Handoff (인수인계) 프로토콜

이 문서는 장시간 진행되는 해커톤 및 복합 개발 환경에서 메인 에이전트의 컨텍스트 오염을 원천 차단하고, 의사결정의 일관성을 유지하며 평가 로그의 품질을 극대화하기 위한 **세션 분할 및 Handoff(인수인계) 표준 운영 지침**입니다.

---

## 1. 세션 분할 및 Handoff의 필요성

### 1) 단일 세션 장기 운용의 치명적 한계
1. **컨텍스트 오염 (Context Pollution):**
   - 수많은 파일 탐색, 테스트 실패 스택 트레이스, 임시 디버깅 출력 등이 누적되면서 에이전트의 주의 집중도(Attention)가 급격히 분산됩니다.
2. **토큰 비용의 기하급수적 급증:**
   - 매 질의마다 앞선 수만 토큰의 대화 기록이 반복 주입되어 응답 지연이 심화되고 토큰 한도에 빠르게 도달합니다.
3. **이전 결정 망각 및 지시 불이행 (Drift):**
   - 초반(10:10~10:30)에 실무자 DM을 통해 확정한 불변의 비즈니스 제약(예: 취소 주문 분모 제외, 특정 파일 보호)을 잊고, 중반 이후 자기 마음대로 코드를 변경하거나 원복하는 참사가 발생합니다.
4. **`/compact` 요약의 한계:**
   - 대화창에서 단순히 `/compact`만 수행하면 LLM이 자체 요약하는 과정에서 세부 제약 조건의 디테일과 실패했던 대안의 맥락이 대거 유실(Lossy Compression)됩니다.

### 2) 고득점 팀의 핵심 비결: 계획된 명시적 Handoff
- 해커톤 상위 3% 성적표에서 가장 높은 평가를 받은 요소는 **정해진 타이밍에 명시적으로 인수인계서(`.probe-kit/runtime/HANDOFF.md`)를 남기고 깨끗한 신규 세션으로 바통을 터치하는 Handoff 스킬**입니다.
- 평가 에이전트 관점에서도 무질서하게 누적된 수천 줄의 세션 로그보다, 정확한 시점에 핵심 결정 사항을 구조화하여 인계하고 새 세션이 이를 복창하며 시작하는 로그가 압도적인 가산점을 받습니다.

## 2. Handoff 실행 4대 골든 타이밍

다음 4가지 상황 중 하나에 해당하면 즉시 작업을 멈추고 Handoff 프로토콜을 가동해야 합니다:

### ⏱️ 타이밍 1: Step 1 핵심 기능 구현 완료 직후 (약 11:15 ~ 11:30)
- **상황:** 초기 환경 확인, EDA 탐색, 요구사항 분석, 첫 번째 핵심 모듈(MVP) 구현 및 단위 테스트 검증이 끝난 시점.
- **목적:** 초기 탐색 과정에서 쌓인 방대한 탐색 로그와 에러 스택을 완전히 털어내고, Step 2/Step 3 확장을 위한 깨끗한 컨텍스트를 확보합니다.

### ⚠️ 타이밍 2: 메인 에이전트가 앞서 합의한 제약을 망각하고 오작동할 때
- **상황:** "취소건은 집계에서 제외하라", "기존 인증 모듈 시그니처를 유지하라"고 합의했음에도 불구하고, 메인 에이전트가 해당 제약을 누락한 채 서브 작업 지시서(`TASK_SPEC.md`)를 발행하기 시작할 때.
- **목적:** 즉각 작업을 중단시키고, 확정된 제약사항을 다시 하드코딩된 체크리스트로 고정한 신규 세션으로 전환하여 헛수고를 차단합니다.

### 🔄 타이밍 3: 대규모 방향 전환 시점 (A안 폐기 후 B안 전환)
- **상황:** 특정 라이브러리 충돌, 메모리 초과(OOM), 또는 복잡도 과다로 인해 기존 방식을 포기하고 다른 아키텍처로 피벗할 때.
- **목적:** 구 세션에 남아있는 실패한 A안의 코드 조각과 설계 편향을 완전히 소거하여, 에이전트가 실패한 방식으로 무의식 회귀하는 것을 방지합니다.

### 🏁 타이밍 4: 구현 종료 및 최종 검증/보고서 모드 진입 직전 (약 12:15)
- **상황:** 모든 기능 구현이 완료되고 남은 시간(약 40분) 동안 종합 회귀 테스트, `SUBMISSION_REPORT.md` 작성, 제출 전 보안 감사(`pre_submit_audit.sh`)를 준비하는 시점.
- **목적:** 코드 수정 권한을 완벽히 동결하고, 오직 검증과 문서 품질에만 집중할 수 있는 깔끔한 제출 전담 세션을 시작합니다.

## 3. Handoff 3단계 표준 프로토콜 (SOP)

```
[1단계: 구 세션]               [2단계: 전환]              [3단계: 신규 세션]
handoff.sh 실행             기존 터미널 종료            신규 세션 기동
      ↓                            ↓                          ↓
기계 정보 자동 수집            새 세션 열기              [프롬프트 6] 주입
      ↓                     (Sol 6.1 xhigh)                   ↓
[프롬프트 5] 메인 보강              ↓                    결정사항 복창
      ↓                       준비 완료                       ↓
HANDOFF.md 확정                                        인간 승인 후 재개
```

### 1단계: 구 세션에서 `handoff.sh` 실행 및 인수인계서 보강
1. 메인 터미널(터미널 1)에서 자동 수집 스크립트를 실행합니다:
   ```bash
   bash .probe-kit/scripts/handoff.sh
   ```
   - 스크립트가 Git 로그, `git diff --stat`, 현재 STATE, 최근 `SUB_RESULT.md` 요약을 읽어 `.probe-kit/runtime/HANDOFF.md`의 골격을 자동 완성합니다.
2. 터미널 1의 메인 에이전트(`Sol 6.1 xhigh`)에게 **[메인 프롬프트 5]**를 전달합니다:
   - 메인 에이전트가 인간과 확정한 [결정-근거-포기한대안], 실무자 DM 제약조건, 그리고 **새 세션이 즉시 수행해야 할 Next Action 1~3가지**를 구체적으로 채워 넣습니다.
3. 인간 사용자가 `.probe-kit/runtime/HANDOFF.md` 파일의 내용을 육안으로 최종 확인합니다.

### 2단계: 기존 세션 종료 및 신규 세션 시작
1. 구 세션 터미널 창을 안전하게 종료합니다 (또는 `/exit`).
2. 신규 터미널 창을 열고 `codex`를 실행합니다.
3. 모델 선택에서 반드시 **`Sol 6.1 (xhigh)`** 모델을 지정합니다.
4. (보조 터미널 2의 서브 에이전트 `Luna 6 xhigh` 창에서도 `/clear`를 실행하여 깨끗한 상태로 대기합니다.)

### 3단계: 신규 세션 인수 및 상태 복창 (인간 승인 후 작업 재개)
1. 신규 세션 터미널 1에 **[메인 프롬프트 6]**을 입력합니다:
   - 지시: *"아직 코드를 절대 건드리지 말고 `.probe-kit/runtime/HANDOFF.md`를 정독한 뒤, (1) 현재 단계, (2) 확정된 결정 및 실무자 제약, (3) 즉시 착수할 Next Action 3가지를 복창하라."*
2. 신규 세션이 복창 내용을 명확하게 출력하면 인간이 이를 검토합니다.
3. 인간이 확인 후 *"복창 내용 확인 완료. 명시된 Next Action 1번부터 차례대로 착수하라"*고 승인하면 작업을 재개합니다.

## 4. `HANDOFF.md` 8대 필수 항목 구성 가이드

인수인계서는 다음 8개 섹션으로 누락 없이 구성되어야 합니다:

| 번호 | 섹션 명칭 | 기술 내용 및 핵심 포인트 |
|---|---|---|
| **1** | **현재 메타데이터** | 작성 시각, 현재 STATE ID 및 단계명, 경과 시간, 잔여 시간, 누적 Git 커밋 수, 인수인계 발생 사유 |
| **2** | **아키텍처 결정 사항** | `[결정]` - `[근거]` - `[포기한 대안]` 3요소 형식으로 기록된 확정 아키텍처 |
| **3** | **실무자 DM 핵심 제약** | 절대 어기면 안 되는 도메인 규칙 체크리스트 (`- [x]` 완료, `- [ ]` 유지) |
| **4** | **코드 및 파일 변경 현황** | `git diff --stat` 기반 변경 파일 목록, 신규 추가 파일, 절대 수정 금지 보호 대상 파일 |
| **5** | **검증 완료 vs 미검증 항목** | 통과된 단위 테스트 명령어와 결과, 아직 미검증된 엣지 케이스 및 실패 경로 |
| **6** | **미해결 리스크 및 기술 부채** | OOM 우려 지점, 임시 하드코딩 파라미터, 성능 병목 후보, 미비된 예외 처리 |
| **7** | **즉시 실행할 행동 (Next Actions)** | 신규 세션이 첫 턴에 실행해야 할 구체적 작업 1~3순위 |
| **8** | **신규 세션 금지 사항** | 비즈니스 코드 직접 작성 금지, 승인 없는 외부 라이브러리 도입 금지 등 Hard Constraints |

## 5. Handoff 실패 방지 5대 체크리스트

1. **미커밋 변경 사항 확인:**
   - Handoff 스크립트 실행 전, 현재까지 동작하는 코드가 있다면 `git commit`으로 명확히 기록해 두었는가?
2. **비즈니스 코드 직접 수정 차단:**
   - 신규 세션의 `Sol 6.1 xhigh`가 첫 턴부터 흥분해서 파이썬/자바스크립트 코드를 직접 고치지 못하도록 프롬프트에 금지 명령을 명시했는가?
3. **독자적인 재해석 금지:**
   - 구 세션에서 합의된 실무자 제약을 신규 세션이 임의로 완화하거나 왜곡하지 않도록 복창 단계를 거쳤는가?
4. **서브 에이전트 컨텍스트 동기화:**
   - 메인 세션을 교체할 때 워커인 서브 에이전트(터미널 2)도 `/clear`를 실행해 낡은 메모리를 비웠는가?
5. **시간 관리:**
   - 전체 Handoff 과정(스크립트 실행 → 보강 → 세션 재기동 → 복창)이 3~5분 이내에 신속하게 완료되었는가?
