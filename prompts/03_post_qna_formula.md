# 마지막 30분 후속 서술형 (6문항 × 5분) 직접 타이핑 만점 공식

이 문서는 과제 제출 직후 치러지는 후속 서술형 확인 문제(6문항 × 5분)에서 감점 없이 최고점을 획득하기 위한 4문장 작성 공식, 질문 전제 불일치 치트키, 6대 유형별 실전 모범 답안 및 타이머 운용 가이드입니다.

---

## 1. 진행 규칙 및 절대 금기 사항 (원문 전문)

* **진행 규칙:** `제출물 확정하고 문제풀기` 클릭 후 약 5~10분간 내 코드와 로그를 바탕으로 맞춤형 확인 문제 6개가 생성됩니다. **`문제 풀기`를 누르면 문항당 5분 타이머가 돌며, AI 사용 불가·외부 창 불가·복사/붙여넣기(`Ctrl+C/V`) 절대 불가·이전 문항 이동 불가**입니다.
* **절대 금기:** 실제로 하지 않은 검증이나 구현을 했다고 거짓으로 적으면 자동 수집된 실행 로그와 대조되어 즉시 감점됩니다. 솔직하게 실제 구현과 한계를 적으세요.
* **출제 메커니즘:** 내가 작성한 코드, git commit/diff, 터미널 실행 로그, 그리고 제출 문서(`SUBMISSION_REPORT.md`)를 평가 에이전트가 교차 분석하여 개인화된 질문을 자동 생성합니다. 따라서 `NOTES_TEMP.md`와 제출 문서에 정리해 둔 `[결정] - [근거] - [검증] - [한계]`가 그대로 서술형 답변의 대본이 됩니다.

## 2. 💡 치트키: 질문의 전제와 내 실제 구현이 다를 때 (원문 전문)

AI 평가 시스템이 내 코드나 로그를 부분적으로 잘못 해석하여 실제와 다른 전제로 질문할 수 있습니다. 이때 당황하거나 거짓으로 맞추려 하지 말고, 공식 가이드 지침에 따라 **"질문의 전제와 내 실제 구현의 차이를 먼저 밝히고 실제로 작업한 내용을 설명"**하면 100% 정상 참작 및 정답 처리됩니다.

### 🔑 전제 불일치 방어 치트키 첫 문장 공식
```text
질문에서는 [A 방식/외부 라이브러리 사용]을 전제로 하였으나, 실제 구현에서는 [B 제약/실무자 요구사항]을 해결하고 불필요한 복잡도를 방지하기 위해 [C 방식/표준 라이브러리 기반 로직]으로 구현했습니다.
```

## 3. ⌨️ 문항당 5분 컷 '4문장 직접 타이핑 템플릿' (머릿속 암기용)

> **1문장 [전제 확인 + 결론(선택한 구조와 이유)]:**  
> *(전제가 다를 때만: "질문에서는 A 방식을 전제로 하였으나, 실제 구현에서는 B 제약을 해결하기 위해 C 방식으로 구현했습니다.")*  
> "저는 현업 요구사항인 `[핵심 목표/예외 조건]`을 안정적으로 충족하고 불필요한 오버엔지니어링을 방지하기 위해 `[내가 택한 구조/로직]`을 선택하여 구현했습니다."
>
> **2문장 [실제 구성 및 코드 동작 원리]:**  
> "구체적으로 `[A 파일/함수]`에서 입력을 받아 `[B 기준/로직]`으로 중복·예외를 처리한 뒤 `[C 형태]`로 결과를 반환하도록 구성했습니다." *(내 실제 코드와 일치해야 함)*
>
> **3문장 [검증 방법 및 근거]:**  
> "정합성을 보장하기 위해 터미널 테스트와 `[표본 데이터 수동 대조 / 내장 브라우저 UI 직접 클릭 검증]`을 실행하여 정상 경로와 예외 케이스에서 모두 의도대로 작동함을 확인했습니다."
>
> **4문장 [한계점 및 실패 조건]:**  
> "다만 현재 구현은 `[대용량 데이터 유입 / 동시성 충돌 / 정의되지 않은 신규 예외 값]` 조건에서는 실패하거나 성능이 저하될 한계가 있어, 향후 `[배치 처리 / 스키마 검증 추가 등]`으로 보완할 수 있습니다."

## 4. 6대 문항 유형별 실전 4문장 모범 답안 (복붙·응용용)

### 유형 1. [설계 판단 및 아키텍처 선택] ("왜 이 구조/패턴을 채택했는가?")
```text
저는 실무자 DM을 통해 확인한 '취소 건 집계 제외 및 최신 중복 데이터 유지'라는 핵심 비즈니스 규칙을 안정적으로 충족하고 복잡한 외부 프레임워크 도입에 따른 오버엔지니어링을 방지하기 위해 표준 라이브러리 기반의 단일 파이프라인 구조를 선택하여 구현했습니다.
구체적으로 clean_data 함수에서 원본 데이터를 스트림 방식으로 읽어 취소 상태 플래그를 필터링하고 동일 ID 중 타임스탬프가 가장 최신인 레코드만 해시맵에 보존한 뒤 정제된 결과를 반환하도록 구성했습니다.
정합성을 보장하기 위해 단위 테스트와 20건의 표본 데이터(취소 및 중복 포함) 수동 대조 검증을 터미널에서 실행하여 정상 집계 수치와 100% 일치함을 확인했습니다.
다만 현재 구현은 모든 연산이 단일 프로세스 메모리 내에서 수행되므로 파일 크기가 수십 GB 이상으로 증가하는 초대용량 유입 환경에서는 OOM(메모리 초과)이 발생할 수 있어 향후 청크 단위 배치 처리 방식으로 보완할 수 있습니다.
```

### 유형 2. [검증 방법 및 정합성 보장] ("구현한 결과물의 정확성을 어떻게 검증했는가?")
```text
저는 과제 지시서의 모호한 요구조건과 데이터 누락 위험을 사전에 차단하기 위해 베이스라인 회귀 테스트와 극단값(Edge Case)을 포함한 표본 수동 교차 검증 방식을 채택했습니다.
구체적으로 tests/test_pipeline.py에 정상 입력 케이스 외에도 결측치(null), 빈 문자열, 음수 수치, 중복 타임스탬프를 포함한 5가지 실패 경로 테스트 케이스를 직접 작성하여 assert 동등성 검증을 수행했습니다.
또한 원본 데이터셋에서 무작위로 추출한 15개 표본의 기댓값을 손수 수동 계산한 뒤 스크립트 출력값과 전수 비교 대조하여 1건의 오차도 없이 통과됨을 터미널 로그로 기록했습니다.
다만 본 검증은 사전에 인지된 결측치 포맷에 한정되어 있으므로 사전에 정의되지 않은 신규 비정형 인코딩이나 비표준 타임존 데이터가 인입될 경우 검증 범위를 벗어날 수 있어 런타임 스키마 검증기를 도입할 필요가 있습니다.
```

### 유형 3. [현재 구현의 한계 및 실패 조건] ("이 시스템이 실패할 수 있는 조건은 무엇인가?")
```text
저는 제한된 시험 시간 내에 핵심 기능(MVP)의 무결성을 최우선으로 확보하기 위해 복잡한 분산 락이나 비동기 큐 대신 동기식 단일 트랜잭션 처리 구조를 선택하여 완성했습니다.
구체적으로 process_records 함수가 순차적으로 데이터를 파싱하고 검증 규칙을 적용하여 최종 결과 파일을 단일 파일시스템에 직렬 쓰기하도록 구성했습니다.
이 방식은 기존 베이스라인 테스트와 단일 스레드 환경의 다중 예외 시나리오에서 결함 없이 완벽히 동작함을 터미널 테스트 로그로 입증했습니다.
하지만 현재 구조는 다수의 작업자가 동시에 쓰기를 요청하는 분산 동시성 환경이나 수백만 건 이상의 대용량 스트림 유입 시 동시 쓰기 충돌이나 타임아웃 지연이 발생할 수 있으므로 프로덕션 배포 시에는 레디스 기반 분산 락 및 메시지 큐(Kafka/RabbitMQ)를 도입해야 합니다.
```

### 유형 4. [AI 활용 및 오케스트레이션/통제] ("AI를 어떻게 활용했고 오버엔지니어링/환각을 어떻게 통제했는가?")
```text
저는 의도 파악과 토큰 비용 절감을 동시에 달성하기 위해 메인 에이전트(Sol 6.1 xhigh)에게는 요구사항 구조화와 작업 명세(TASK_SPEC.md) 작성만 전담시키고 서브 에이전트(Luna 6 xhigh)에게 코드 구현과 단위 테스트 실행을 분리 위임하는 듀얼 터미널 방식을 적용했습니다.
구체적으로 메인 에이전트가 불필요한 전역 상태 관리나 거창한 디자인 패턴을 제안했을 때 프롬프트를 통해 이를 즉시 배제하고 실무자 DM으로 확정된 조건만 담긴 단일 모듈 지시서를 작성하도록 엄격히 통제했습니다.
또한 서브 에이전트가 각 모듈 작성을 마칠 때마다 SUB_RESULT.md 요약 보고와 git diff를 확인한 뒤 즉시 /clear를 실행하여 누적 컨텍스트 오염과 AI 환각(Hallucination)을 원천 차단했습니다.
다만 이러한 엄격한 분리 통제 방식은 모듈 간 경계가 모호하거나 긴밀한 전역 결합이 필요한 대규모 리팩토링 시 메인의 작업 명세 작성 비용이 다소 증가하는 한계가 있어 명세 템플릿의 자동화로 개선할 수 있습니다.
```

### 유형 5. [대안 비교 및 포기한 이유] ("다른 대안은 무엇이었으며 왜 현재 방식을 선택했는가?")
```text
(전제 불일치 대비 방어 포함) 질문에서는 판다스(Pandas)나 복잡한 외부 분석 프레임워크 도입을 전제로 하였으나, 실제 구현에서는 외부 의존성 설치 제약과 런타임 오버헤드를 방지하기 위해 파이썬 내장 표준 라이브러리(csv, json, math) 기반의 경량 파이프라인을 채택했습니다.
초기에는 정규표현식 기반의 일괄 치환 방식을 대안으로 검토했으나 대용량 데이터 파싱 시 역추적(Backtracking) 성능 저하 및 다중 컬럼 상호 의존 규칙 처리에 취약하여 배제하고 상태 전이 기반의 명시적 조건 분기 로직으로 구성했습니다.
검증을 위해 1,000건의 합성 데이터에 대해 두 방식의 실행 시간과 메모리 점유율을 터미널에서 프로파일링하여 경량 파이프라인이 3배 이상 빠르고 정합성이 높음을 확인했습니다.
다만 현재의 순수 파이썬 구현은 C 확장을 사용하는 고도로 벡터화된 연산 라이브러리보다는 초대형 행렬 연산 속도에서 한계가 있을 수 있어 추후 대규모 수치 연산 도입 시 넘파이(NumPy) 도입을 고려할 수 있습니다.
```

### 유형 6. [확장성 및 프로덕션 고도화] ("향후 실제 서비스 배포를 위해 무엇을 추가해야 하는가?")
```text
저는 현재 프로토타입 단계에서 실무자 에이전트가 요청한 핵심 유저 동선과 업무 규칙의 기능적 정합성을 100% 충족하는 MVP 형태로 시스템을 설계하고 구현했습니다.
구체적으로 웹 서비스 백엔드를 0.0.0.0 호스트에 바인딩하고 내장 Browser 조작을 통해 정상 입력과 유효하지 않은 예외 입력에 대한 에러 핸들링 응답을 사용자 화면에 정확히 표출하도록 구성했습니다.
터미널에서 서버 기동 로그를 확인하고 내장 브라우저에서 직접 버튼 클릭, 양식 제출, 페이지 라우팅 동작을 수행하여 UI와 백엔드 간 연동 상태를 실시간으로 교차 검증했습니다.
향후 실제 사내 인트라넷에 프로덕션으로 배포하기 위해서는 JWT 기반 사용자 세션 인증 연동, 정적 파일 CDN 분리, 헬스체크(/healthz) 엔드포인트 구축 및 시스템 모니터링 메트릭(Prometheus) 수집 환경을 보완해야 합니다.
```

## 5. 5분 타이머 분초 운용법 (문항당 300초 실전 배분)

후속 서술형은 복사/붙여넣기가 원천 차단되므로 순수 키보드 직접 타이핑으로 승부해야 합니다. 문항당 주어진 5분(300초)을 아래와 같이 분초 단위로 엄격히 관리하세요:

```text
[00:00 ~ 00:50] (50초) 질문 분석 & 매핑
- 질문의 핵심 키워드(설계 이유, 검증 방법, 한계 조건 등) 파악.
- 질문의 전제가 내 실제 구현과 일치하는지 판별. (다르면 즉시 '질문에서는 A를 전제로 하였으나 실제로는 B로 구현했다' 치트키 도입 결정).
- 제출 문서(SUBMISSION_REPORT.md)의 [결정]-[근거]-[검증]-[한계] 중 해당 섹션 머릿속 매핑.

[00:50 ~ 03:20] (150초) 4문장 직접 타이핑
- 1문장: [결론 & 선택 이유] ("저는 ~를 위해 ~구조를 채택했습니다.")
```
